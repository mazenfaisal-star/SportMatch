# SportMatch — النسخة الأولية 0.1

واجهة تطبيق رياضي متجاوبة باللغة العربية (RTL) مبنية بـ React + Vite، مع تسجيل دخول جاهز للربط بـ Supabase.

## الموجود في النسخة الحالية

- شاشة تسجيل دخول وإنشاء حساب بالبريد وكلمة المرور، واستعادة كلمة المرور.
- أزرار Google وFacebook OAuth (تحتاج تفعيل المزودين وإضافة مفاتيحهما في Supabase).
- وضع تجريبي لتستكشف الواجهة من دون إنشاء حساب أو قاعدة بيانات. كل البيانات التي تظهر في هذا الوضع أمثلة وليست بيانات حقيقية.
- خطوة إعداد بعد تسجيل الدخول لاختيار نوع الحساب: لاعب أو مدرب/كابتن.
- اللاعب يختار الرياضة والمستوى الحالي والهدف والموقع، ويمكنه تحديد إن كان يتدرب مع مدرب واختيار مدرب عام موجود في الدليل.
- المدرب يضيف الرياضات التي يدربها، والخبرة والمؤهلات المعلنة والشهادات ومكان العمل والأكاديمية والأسعار ونوع التدريب.
- لوحة تحكم عربية وقائمة جانبية، ودليل رياضات ومدربين، وصفحات الملف الشخصي وسجل التدريب والتقييمات والبطولات التجريبية والإعدادات.
- إضافة جلسة تدريب وتقييم مهارة من داخل الواجهة. يتم حفظها في Supabase عند ربط المشروع؛ وفي الوضع التجريبي تتغير داخل الواجهة فقط.
- ملف SQL مرفق لإنشاء الجداول الأساسية وسياسات Row Level Security.

## المتطلبات

- Node.js بإصدار حديث (يفضل الإصدار LTS).
- حساب Supabase.
- حسابات مطورين في Google Cloud وMeta/Facebook فقط إذا أردت تفعيل تسجيل الدخول الاجتماعي.

## تشغيل الواجهة محليًا

1. فك ضغط مجلد المشروع.
2. افتح Terminal أو PowerShell داخل مجلد `SportMatchApp`.
3. نفّذ:

```bash
npm install
npm run dev
```

4. افتح عنوان التطوير الذي يظهر في الطرفية، غالبًا `http://localhost:5173`.
5. قبل ربط Supabase يمكنك الضغط على «استكشف النسخة التجريبية» لمعاينة الواجهة.

## ربط Supabase

### 1) أنشئ مشروع Supabase

1. أنشئ مشروعًا جديدًا في لوحة Supabase.
2. افتح قسم **SQL Editor**.
3. افتح الملف `supabase/schema.sql` الموجود داخل هذا المشروع، وانسخ محتواه إلى SQL Editor ثم شغّله مرة واحدة.
4. احتفظ بـ **Project URL** و**Publishable key** من قسم Connect أو إعدادات API بالمشروع.

### 2) أضف إعدادات البيئة

1. انسخ `.env.example` إلى ملف جديد اسمه `.env.local` في جذر المشروع.
2. ضع القيم الحقيقية مكان القيم التجريبية:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_SUPABASE_PUBLISHABLE_KEY
```

3. أوقف خادم التطوير ثم شغّله من جديد باستخدام `npm run dev`.

**مهم جدًا:** لا تضع `service_role` أو أي `secret key` في متغير يبدأ بـ `VITE_` أو في ملفات الواجهة. الواجهة تستخدم المفتاح القابل للنشر فقط، ويعتمد الوصول للبيانات على سياسات RLS في قاعدة البيانات.

### 3) إعداد البريد الإلكتروني

1. من لوحة Supabase افتح **Authentication → URL Configuration**.
2. اجعل Site URL أثناء التطوير `http://localhost:5173`.
3. أضف `http://localhost:5173/**` إلى قائمة Redirect URLs المسموح بها. بعد النشر أضف عنوان الموقع المنشور أيضًا.
4. افتح **Authentication → Sign In / Providers** وتأكد من تفعيل Email.
5. حدّث قالب رسالة تأكيد البريد أو استعادة كلمة المرور من إعدادات Email Templates حسب هوية SportMatch.
6. خدمة الإرسال الافتراضية مناسبة للاختبار المحدود فقط، وللاستخدام مع لاعبين حقيقيين ينبغي إعداد SMTP مخصص موثوق داخل Supabase حتى تصل الرسائل لجميع المستخدمين وبمعدل مناسب.

### 4) إعداد Google OAuth (اختياري)

1. أنشئ OAuth Client من نوع Web application في Google Cloud Console.
2. داخل صفحة Google Provider في Supabase انسخ **Callback URL** الخاص بمشروعك.
3. أضف Callback URL في Google Cloud ضمن Authorized redirect URIs.
4. انسخ Google Client ID وClient Secret إلى صفحة Google Provider في Supabase، ثم فعّل المزود واحفظ.
5. تأكد أن `http://localhost:5173` وعنوان الموقع المنشور موجودان ضمن Redirect URLs في Supabase URL Configuration.

### 5) إعداد Facebook OAuth (اختياري)

1. أنشئ تطبيقًا من Meta for Developers وفعّل Facebook Login.
2. أضف Callback URL الذي يعرضه Supabase Facebook Provider ضمن Valid OAuth Redirect URIs في Meta.
3. فعّل صلاحيات `public_profile` و`email` المطلوبة لتدفق تسجيل الدخول.
4. أدخل App ID وApp Secret في Supabase ضمن Facebook Provider ثم احفظ.
5. تطبيق Meta الجديد يكون عادة في وضع التطوير؛ اختبره بحسابات أضيفت كأدوار/مختبرين قبل نشره للجميع.

## نموذج العمل وقاعدة البيانات

الملف `supabase/schema.sql` ينشئ الجداول التالية:

- `profiles`: الاسم ونوع الحساب والرياضة والمستوى والموقع وإعداد ظهور الملف.
- `player_profiles`: هدف اللاعب، هدف قصير المدى، ومعلومات ارتباطه بمدرب.
- `coach_profiles`: تخصصات المدرب وخبرته ومؤهلاته المعلنة والأكاديمية والسعر ونوع التدريب وحالة التحقق.
- `training_logs`: جلسات التدريب والملاحظات والخطوات التالية.
- `skill_assessments`: تقييمات المهارات بتاريخها؛ الإضافة تسجّل تقييمًا جديدًا بدل محو القديم.

## ما الذي ما زال نموذجًا أوليًا؟

- لا توجد حجوزات أو مدفوعات فعلية حتى الآن.
- قسم البطولات يحتوي بيانات تجريبية توضيحية، وليس قائمة بطولات مؤكدة.
- لا توجد خريطة فعلية بعد؛ ينبغي إضافتها عندما تتوفر مواقع دقيقة ومتحقق منها.
- علامات التحقق في ملف المدرب موجودة كحقول قاعدة بيانات، لكنها لا تصبح «تم التحقق» إلا بعد إنشاء إجراءات تحقق فعلية ومراجعة بشرية مناسبة.
- الربط بالمدرب يتم حاليًا وفق اختيار اللاعب من الدليل. لذلك فهذه نسخة تطوير أولية وليست جاهزة لفتح بيانات حساسة على نطاق عام؛ قبل الإطلاق العام، يجب إضافة طلب ربط يتطلب موافقة اللاعب والمدرب معًا، وسجل واضح للمنح والإلغاء.
- سياسات SQL المرفقة بداية عملية للـ MVP، ويجب مراجعتها واختبارها على بيئة تجريبية قبل تخزين بيانات أشخاص حقيقية. أضف اختبارات RLS وخطة نسخ احتياطي وسياسة خصوصية قبل الإطلاق العام.
- لا تجمع بيانات حساسة لا تحتاجها، ولا تعرض سجل التدريب أو التقييمات في الملف العام.

## بناء نسخة للنشر

```bash
npm run build
```

يُنتج Vite مجلد `dist`. عند النشر على استضافة للواجهات الثابتة، أضف متغيرات البيئة نفسها في إعدادات الاستضافة واضبط عنوان النشر ضمن Supabase Redirect URLs.

### النشر على Vercel

1. ارفع المشروع إلى مستودع Git خاص، مع `package-lock.json`، ومن دون `.env.local` أو `node_modules` أو `dist`.
2. في Vercel استورد المستودع؛ إعدادات البناء هي `npm run build` ومجلد الإخراج `dist`.
3. أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` في Project Settings → Environment Variables لكل بيئة مطلوبة، ثم أعد النشر. استخدم Publishable Key فقط.
4. بعد ظهور نطاق Vercel، أضف النطاق إلى Supabase Authentication → URL Configuration → Redirect URLs، وحدّث Site URL إلى نطاق الإنتاج.
5. اختبر إنشاء الحساب وتأكيد البريد وتسجيل الدخول واستعادة كلمة المرور على النطاق المنشور. إعداد `vercel.json` يعيد صفحات التطبيق إلى `index.html`.

### بناء نسخة Android قابلة للتثبيت

1. أضف إلى GitHub Actions Secrets القيمتين `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY`؛ لا تستخدم مفتاح `service_role`.
2. في Supabase Authentication → URL Configuration، أضف عنوان الرجوع `com.sportmatch.app://auth/callback` إلى Redirect URLs، إلى جانب نطاق Vercel.
3. شغّل سير العمل **Build Android APK** من تبويب Actions أو ادفع التغييرات إلى فرع `main`.
4. نزّل ملف `SportMatch-Android-APK` من Artifacts في نتيجة التشغيل. هذه نسخة Debug للتجربة والتثبيت المباشر؛ نشر إصدار رسمي على Google Play يحتاج إعداد توقيع Release ومراجعة متطلبات Play Console.
5. النسخة تستخدم واجهة التطبيق المضمّنة داخل الحزمة. كل تغيير في الواجهة يتطلب بناء APK جديدًا.

## الأمان قبل النشر

تمت إضافة طبقة تقوية أولية للمشروع. قبل فتح التسجيل للجمهور:

1. انسخ `.env.example` إلى `.env.local` وضع `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` فقط. لا تضع `sb_secret_` أو مفتاح `service_role` أو كلمة مرور قاعدة البيانات في أي متغير يبدأ بـ `VITE_`.
2. لا تشغّل SQL على قاعدة موجودة قبل معرفة الملفات المطبقة وأخذ نسخة احتياطية. على قاعدة جديدة: طبّق `schema.sql` ثم `security_hardening.sql` ثم `admin_console.sql`. على قاعدة قائمة، راجع سجل التغييرات أولًا ولا تعِد تشغيل `schema.sql` أو أي ترحيل سبق تطبيقه.
3. استخدم HTTPS عند النشر، وأضف عنوان التطبيق المنشور وعناوين إعادة التوجيه الدقيقة في Supabase Authentication → URL Configuration.
4. في Supabase Authentication → Settings/Rate Limits، راجع حدود البريد وتسجيل الدخول. اضبط الحد الأدنى لكلمات المرور على 12 حرفًا على الأقل، وفعّل حماية كلمات المرور المسربة إذا كانت الخطة تدعمها، مع تفعيل تأكيد البريد الإلكتروني.
5. لا تفعّل Google أو Facebook إلا بعد إعداد بيانات المزود في Supabase وإضافة عناوين الرجوع المسموح بها في إعدادات المزود.
6. ملف `vercel.json` يضيف رؤوس حماية للواجهة المنشورة على Vercel. إذا استخدمت استضافة أخرى، انقل إعدادات الرؤوس إلى إعدادات الاستضافة المقابلة واختبر سياسة CSP.
7. قبل النشر، نفّذ `npm ci` ثم `npm audit --audit-level=moderate` و`npm run build` و`npm run check:secrets`. احتفظ بملف القفل وارفعه إلى Git.
8. لوحة Admin الحالية تستخدم دوال RPC وصلاحيات قاعدة البيانات. لا تعتبرها جاهزة على مشروعك قبل التأكد من تطبيق `admin_console.sql` واختبار الرفض لحساب عادي.

### ملاحظات تقنية

- كلمات المرور تُدار بواسطة Supabase Auth وتُخزّن على الخادم بعد تجزئتها؛ لا يخزن التطبيق كلمة المرور في جدول `profiles` ولا ينفّذ تجزئة كلمات مرور بنفسه.
- مفتاح Supabase Publishable/anon ليس سرًا ويمكن أن يظهر في تطبيق المتصفح؛ الحماية الحقيقية تعتمد على RLS والصلاحيات. المفاتيح السرية ومفتاح `service_role` لا يجوز تضمينهما في الواجهة.
- لا يوجد حاليًا خادم API مخصص؛ عمليات بيانات المستخدم تذهب مباشرة إلى Supabase وتخضع لسياسات RLS. وظائف الإدارة محمية عبر RPC في قاعدة البيانات.
- CORS الخاص بواجهات Supabase المُدارة ليس إعدادًا تضبطه من `vercel.json`. لا تضف رؤوس `Access-Control-Allow-Origin: *` إلى الواجهة. إذا أضفت Edge Functions لاحقًا، قيد Origins فيها إلى نطاقاتك الفعلية.
- `npm run dev` مربوط بـ `127.0.0.1` حتى لا يُعرَض خادم التطوير على الشبكة المحلية افتراضيًا.
- Android مبني على Capacitor؛ يستقبل التطبيق روابط تسجيل الدخول واستعادة كلمة المرور عبر `com.sportmatch.app://auth/callback`.


## لوحة الإدارة (الإصدار الأول)

لإضافة لوحة إدارة محمية، راجع `ADMIN_SETUP_AR.md` ثم شغّل `supabase/admin_console.sql` بعد ملفات `schema.sql` و`security_hardening.sql`. لا يظهر رابط لوحة الإدارة إلا للحساب الذي تتم ترقيته يدويًا إلى `public.platform_admins`. لا تضع مفاتيح Supabase السرية في الواجهة، ولا تضف زر تسجيل عام كمسؤول.
